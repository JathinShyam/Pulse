# API Reference

The live OpenAPI schema is generated by `drf-spectacular` when
`ENABLE_DOCS=True`:

- Swagger UI: `/api/docs/`
- ReDoc: `/api/redoc/`
- OpenAPI JSON: `/api/schema/`

The docs routes are public; the data endpoints they describe require
authentication.

## Authentication

Two schemes are supported. Send one credential per request:

| Scheme  | Header                                               | Used by                               |
| ------- | ---------------------------------------------------- | ------------------------------------- |
| API key | `X-API-Key: <key>` or `Authorization: Api-Key <key>` | server-to-server clients              |
| JWT     | `Authorization: Bearer <access>`                     | browser console via the Next.js proxy |

`Authorization: Bearer <api-key>` is rejected. No data endpoint has an
anonymous or development bypass. Configure client keys with `PULSE_API_KEYS`
(comma separated); an empty list rejects all API-key requests.

Browser operators log in with `POST /api/auth/login/` using an email address or
username. The backend returns an access/refresh pair; the Next.js proxy stores
them in httpOnly cookies and never returns the tokens to browser JavaScript.
Login and registration are throttled. Registration is disabled unless
`ALLOW_REGISTRATION=True`.

## Send a notification

```http
POST /api/notifications/send/
Content-Type: application/json
X-API-Key: <key>
```

```json
{
  "user_id": "user_123",
  "template_name": "otp_login",
  "to": "+14155550123",
  "context": { "code": "123456" },
  "idempotency_key": "otp-user_123-1",
  "priority": "high"
}
```

`channel` is optional and defaults to the template channel. It must be one of
`email`, `sms` or `push`. Email recipients must be valid email addresses; SMS
recipients must be E.164 numbers (for example `+14155550123`); push uses the
recipient or an explicit `device_token`.

Optional top-level `subject`, `body` and `title` values override the template
and are rendered with the same `context`. Missing template variables return
`400`.

Responses:

| Status                    | Meaning                                                                                                      |
| ------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `202 Accepted`            | New row persisted and queued; body has `notification_id` and `status: "queued"`                              |
| `200 OK`                  | Idempotency key already belongs to the same request; returns the existing notification ID and current status |
| `400 Bad Request`         | Invalid template, recipient, context or query parameter                                                      |
| `401 Unauthorized`        | Missing or invalid credential                                                                                |
| `409 Conflict`            | Idempotency key already used for a different request                                                         |
| `429 Too Many Requests`   | Per-principal/target-user/channel rate limit; see `Retry-After`                                              |
| `503 Service Unavailable` | The broker could not accept the task; row is marked `failed`. Retry with a new key after the broker recovers |

Delivery is asynchronous. `202` means the request was accepted, not delivered.
Delivery is at-least-once in a narrow crash window after provider
acknowledgement; see the known limitations for details.

## Status, list and templates

```http
GET /api/notifications/status/{uuid}/
GET /api/notifications/list/?user_id=user_123&channel=email&status=sent&limit=50
GET /api/notifications/templates/
GET /api/notifications/templates/{uuid}/
```

`limit` is validated from 1 to 200. `channel` is one of `email`, `sms`, `push`;
`status` is one of `pending`, `sending`, `sent`, `failed`, `retrying`.
Status and list reads are scoped: an API key sees only rows it created, a
non-staff JWT user sees rows they created, and staff users see all rows. A row
outside the caller's scope returns `404`, not `403`, so existence is not leaked.

Templates are installation-wide and readable by any authenticated principal.

## Metrics

```http
GET /api/metrics?window=24h
```

`window` is one of `1h`, `24h`, `7d`, `30d` (default `24h`). The response is
computed from retained rows for the caller's scope:

```json
{
  "window": "24h",
  "generated_at": "2026-10-22T15:00:00Z",
  "total": 120,
  "previous_total": 100,
  "volume_change_pct": 20.0,
  "by_status": {
    "pending": 2,
    "sending": 0,
    "sent": 110,
    "failed": 5,
    "retrying": 3
  },
  "deliverability": 95.65,
  "latency": { "p50_ms": 40.0, "p95_ms": 80.0, "avg_ms": 50.0 },
  "avg_attempts": 1.2,
  "throughput_per_min": 0.083,
  "channels": [
    {
      "channel": "email",
      "total": 80,
      "sent": 75,
      "failed": 3,
      "retrying": 1,
      "pending": 1,
      "sending": 0,
      "success_rate": 96.15,
      "avg_latency_ms": 48.0,
      "p95_latency_ms": 72.0
    }
  ],
  "series": [
    {
      "bucket": "2026-10-22T00:00:00Z",
      "email": 80,
      "sms": 20,
      "push": 20,
      "total": 120
    }
  ],
  "templates": 7
}
```

`deliverability` and per-channel `success_rate` are `sent / (sent + failed)` and
are `null` when there are no terminal rows. Latency is measured from row
creation to provider acknowledgement and is `null` when unavailable. There is no
average-latency substitution for a missing p95. The compact
`total_volume`/`volume_trend` fields remain for older clients but are derived
from the same real total.

## Health and operations

- `GET /health/` – process liveness; bypasses host/HTTPS checks.
- `GET /readyz/` – checks PostgreSQL and Redis; returns `503` if either is down.
- Prometheus exporter – internal `:8001/metrics`, not routed through the public
  ingress.
- Flower and the Compose-only Streamlit dashboard – internal-only tooling; no
  built-in multi-user authentication.

## Errors and limits

Send requests are rate limited by principal, target `user_id` and channel
(`RATE_LIMIT_MAX_REQUESTS` per `RATE_LIMIT_WINDOW_SECONDS`, default 10 per 60s).
An optional `API_THROTTLE_RATE` adds an API-wide DRF throttle. Login defaults to
10 attempts per minute and registration to 5 per hour; both are configurable.

The request body limit is 256 KiB. Delivery retries use exponential backoff and
stop at `NOTIFICATION_MAX_RETRIES` (5 by default). `sent` and `failed` are
terminal and are never overwritten by a late worker execution.
